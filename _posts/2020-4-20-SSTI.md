Template engines are becoming a popular choice in today's webapp ecosystem and with them come a type of vulnerability known as SSTI, or Server Side Template Injection. A template engine uses static template files which at runtime replace variables or placeholders with actual values in the HTML page. This results in a webpage that appears more dynamic. SSTI vulnerabilities occur when user-controlled input is embedded within a template in an unsafe manner or when. SSTI vulnerabilities look similar to XSS vulnerabilities however, SSTIs vulnerabilities are executed server side which is inherently more dangerous (as the user can gain control of the server). 

Examples of such template engines are: Twig, Freemarker, Flask, Jinja2.

Let’s look at the examples provided by <a href="https://portswigger.net/research/server-side-template-injection">James Kettle</a> to better understand what is going on with SSTI vulnerabilities.

Let’s say we are using the Twig template to customize our greetings to users who sign up for our marketplace.

{% highlight php %}
$output = $twig->render("Dear {first_name},", array("first_name" => $user.first_name) );
{% endhighlight %}

This example is fine because it is simply passing the user-controlled name into the variable of first_name. 

However, things become a bit more dangerous with the next example:

{% highlight php %}
$output = $twig->render($_GET['custom_email'], array("first_name" => $user.first_name) );
{% endhighlight %}

Here, the user can control the contents of the template itself and what is rendered in the email via the custom_email GET parameter, rather than simply passing a name into it. While this does create an XSS vulnerability, the SSTI vulnerability here enables the user to control what happens server-side. 

This type of vulnerability arises when developers allow for sandbox options for their templates, enabling users to control or edit templates how they see fit. It can also unintentionally occur when user input is concatenated directly into a template. Sound familiar? It should, as it's similar to what occurs with SQL injections (please check out my previous post if you’d like to learn a bit more on SQL injection). 

To learn more about SSTI vulnerabilities and better understand Jame Kettle’s research, I set up <a href="https://github.com/s4n7h0/xvwa">XVWA</a> (Xtreme Vulnerable Web App) which is an intentionally vulnerable web application (with an SSTI component).

After I have the webapp up and running, I navigate to the SSTI pane.

Here we have a basic webapp where a user can submit their name. Now, we have an advantage already knowing the type of template engine that is running (and also the fact we know there is an SSTI vulnerability) but we are going to walkthrough it following the steps of Detect, Identify, Exploit, which again are outlined in James Kettle's research. 


### Detect

There are various ways one can detect a potential SSTI, but here, we will use a simple math problem. Since the name submission is the only place on the page that manipulates data, we can deduce that the name submission is our injection point.

![Detect](/images/ssti/detect.png)

We can see that instead of \{\{50+5\}\} being read as a string, the web application reads the user input as integers and performs math. It was likely expecting a string and something behind the scenes is not concatonating and/or not filtering the user input properly, ergo it does not read the data as a string but as integers being added together. 

### Identify

The next step is to identify which template engine is being used. XVWA has unfortunately already spoiled the template engine in question (Twig). In general, however, we can engage in various probing methods, such as submitting different types of template engine syntax to see what is accepted, what errors out, etc. 

This tree for identifying templates is helpful:

![Identify Tree](/images/ssti/identify-table.png)

So let's pretend we don't know which template engine is being used, and we submit \{\{7*'7'\}\}

![Identify](/images/ssti/identify.png)

Due to the resulting 49, we now know that we're working with Twig. If it had been Jinja2, the result would be 7777777. If it had been neither a resulting 49 or 7777777, we would know to test other submissions for different template enginges. 

### Exploit

After discovering which template engine is being used, we should read the documentation to better understand how we might exploit it. Another helpful resource that I use often in engagements is the PayloadsAllTheThings github, which has a nice resource on SSTI injections and specifically payloads relevant to Twig. However, while an amazing reference, we shouldn't be blindly plugging stuff in.

<a href="https://github.com/swisskyrepo/PayloadsAllTheThings/tree/master/Server%20Side%20Template%20Injection#twig">PayloadsAllTheThings: Twig</a>

Let’s take a look at one of these examples and examine what's going on behind the scenes.

![Markdown blows](/images/ssti/undefinedFunctiontwig.png)

Twig is built on PHP. It has a function **registerUndefinedFilterCallback()** that allows us to register native PHP functions as Twig functions. Thus, in the code snippet above, we are effectively registering php’s **exec()** function as a Twig function. Php's **exec()** function is used to execute an external program and returns the last line of the output. 

I’m not entirely sure how the **getFilter()** function works but somehow it uses the aforementioned defined function and extends its functionality to run the provided command (if anyone can better explain this please feel free to email me, I've read the docs but am still unsure). Here we are using it to specify which shell commands we want **exec()** to execute.

![Get ID](/images/ssti/get-id.png)

**Exec()** works for us here because we are not attempting an information overflow, but trying to execute stuff on the server. If we wanted to retrieve the /etc/passwd file, for example, php's '**shell_exec()**' function would be more useful to us as we wouldn't be limited to receiving one line of output.

![exec()](/images/ssti/exec-passwd.png)

![shell_exec()](/images/ssti/shellexec-passwd.png)
